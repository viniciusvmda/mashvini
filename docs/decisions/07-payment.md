# 07 - Payment

- Persisting the order as `pending` on "Finalize order" and paying it in a separate request, over creating the order and paying it in a single request, so the stock is held while the client is at the payment screen. With a single request, the last unit could be bought by another kiosk while the client is tapping their card.
- `status` on `order` with `pending | paid | cancelled | expired`, the values these transitions actually use, as planned in [order decision](06-order.md). `expired` is kept apart from `cancelled` so abandoned sessions can be told apart from clients who cancelled.
- Expiry (`expires_at` + a periodic sweep) over relying only on the frontend to cancel, since a closed tab, a lost network or a crashed tablet would otherwise hold stock forever. The frontend idle timeout cancels first (~100 s). The 5 minute backend expiry is the safety net.
- In-process asyncio task in the FastAPI lifespan for the sweep, over Celery/a cron container/`pg_cron`, since it's a single small query per minute and needs no new infrastructure. `FOR UPDATE SKIP LOCKED` keeps it safe if more than one API instance ever runs.
- Simulated payment machine (select the method, finish on the machine) over a card number/expiry/CVC form, since a real self-service kiosk takes payment through a payment machine and the client never types card data. It also keeps card data out of the app entirely (no PCI scope, nothing sensitive to store). The trade-off is less input validation to show, which the rest of the flow already covers (quantities, stock, request schemas).
- Dev-only simulated machine panel (Approve / Decline / Gateway error) over an always-approving mock
- The 5 second machine wait on the client over a sleep inside the mock gateway, so the order row isn't locked and a database connection isn't held while the client is at the machine, and "Back to cart"/"Cancel order" still work during the wait. The mock sits behind a `PaymentGateway` interface injected as a dependency, so a real provider can replace it without touching the endpoint.
- `Idempotency-Key` header per payment attempt, plus disabling the screen while processing, over only disabling the button. Replaying the key returns the stored result instead of charging twice.
- Payment amount computed by the backend from `order_line.price`, over receiving it from the client, for the same reason stock is re-read on order creation: never trust client-side values.
- A `payments` table with one row per attempt, over payment columns on `order`, since a declined attempt followed by an approved one is a normal flow and both are worth keeping for traceability.
- Declined payments keep the order `pending` so the client can try again, over cancelling on the first decline, since a kiosk client with a second card shouldn't have to rebuild their cart.
- No idempotency key on `POST /orders`: disabling "Finalize order" while in flight covers the double tap, and an orphan `pending` order from a lost response expires and releases its stock on its own.
