# 06 - Order

- Side panel over a full-size cart screen for reviewing the order, since the main target device is a tablet in landscape, which has enough width to keep the catalog and the cart visible at the same time. A full-size cart would require an extra navigation round-trip (open cart, go back to add more items) and would hide the catalog while reviewing.
- Fixed `Header` (app name + cart summary) and `Footer` (send/cancel actions) over letting them scroll with the catalog/cart content, so the cart status and order actions stay reachable on a long catalog without scrolling back to the top or bottom, which matters on a touch kiosk where every extra scroll is friction.
- Single database transaction for re-checking stock, decrementing it, and inserting the order and its order lines, over separate transactions for the order and the order lines, since a partial result (order without lines, or stock decremented without a persisted order) would leave the
  data inconsistent. This reinforces the ACID requirement from [data persistence decision](03-data-persistence.md).
- Custom domain exceptions (e.g. `ItemNotAvailableError`) mapped to FastAPI exception handlers over inline `HTTPException` raises in the endpoint, for reuse and a consistent error response shape across endpoints as more error cases are added.
- `order_line` stores its own `price`, captured at order time, over reading `item.price` at query time, so a later price change on the item doesn't rewrite the price of past orders.
- No `status` field on `order` yet, over adding it now with `pending`/`paid`/`cancelled` values. Because order creation is atomic (below), every order that gets persisted in this task has already fully succeeded. The payment task is the right place to add `status`, with values that its own transitions actually use depending on the way I implement it.
- Order/order lines are only persisted once, atomically, when the client sends the order over persisting a draft order as items are added to the cart. The cart itself stays frontend-only state, simplifying the logic: keeps stock untouched (and reservable by any client) throughout browsing, avoids extra endpoints (update/cleanup order). As a result, cancelling before sending the order is a frontend-only action. There's no order row yet to cancel.
- React's built-in `createContext`/`useContext` with `useReducer` for the cart state over Redux or another external store. `useReducer` gives cart actions built-in with less boilerplate and no need for middlewares, dev tools or other features.
- Real Postgres over SQLite for the order creation integration tests, since the concurrent-stock edge case (two clients racing for the last unit) is exactly what the single-transaction design above exists to handle, and it depends on Postgres's row locking. SQLite is a single-writer, whole-file-lock engine with no real `SELECT ... FOR UPDATE`, so it wouldn't exercise that behavior. Postgres is already in docker-compose, so this only adds a service container to the backend CI job, not new infra.
- `tests/unit/` and `tests/integration/` as separate top-level folders. Almost every case worth testing for order creation is a persistence case, so mocking the database only validates pure request-validation checks. Pushing the real coverage to an integration tier only pays off if that tier can be skipped for fast local iteration and run on its own in CI without slowing down the unit tests.
- Idle timeout with a warning dialog and its own countdown, over silently resetting the cart on inactivity, since a customer who's still there but just slow (reading labels, counting change, deciding) shouldn't lose their cart without a chance to say so. This is a self-service kiosk with no cashier to un-cancel a mistake for them, so the reset needs to be recoverable up to the last second. Reuses the same countdown pattern already built for the success screen instead of a different mechanism.
